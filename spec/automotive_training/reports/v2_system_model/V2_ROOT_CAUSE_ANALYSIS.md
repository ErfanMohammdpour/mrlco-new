# V2_ROOT_CAUSE_ANALYSIS — چرا سیاست از `all_MEC` می‌بازد

> ⚠️ **این حکم در بخش «تصحیح (نسخهٔ ۲)» در انتهای سند باطل شده است. آن بخش را بخوان.**

**حکم اصلی (نسخهٔ ۱، باطل‌شده): این یک شکست یادگیری نیست، یک شکستِ صورت‌بندی (formulation) است.**

بودجهٔ انرژی روی **۰.۵ × E_mec** تنظیم شده، در نتیجه **`all_MEC` طبق ساختار غیرممکن
(infeasible) است** — چون `E_mec` خودش دقیقاً همان anchor و scale است. پس قید انرژی سیاست را
**مجبور** می‌کند از MEC فاصله بگیرد، در حالی که `all_MEC` تقریباً بهینهٔ latency است
(فقط ۴.۹٪ بدتر از اوراکل پنل). نتیجه: یک مصالحهٔ Lagrangian که هیچ‌کس نمی‌خواست.

## 1. زنجیرهٔ شواهد (همه از artifact های خود اجرا)

### 1.1 سیاست واقعاً کجا ایستاده

| candidate | latency (s) | نسبت |
|---|---|---|
| `candidate_oracle_s` | 0.028452 | ۰.۹۵× |
| `all_MEC` (تک‌action، بدون جست‌وجو) | 0.029931 | **۱.۰۰×** |
| `greedy_coordinate_descent_MC` | 0.031239 | ۱.۰۴× |
| `heft_reference_v2` | 0.032665 | ۱.۰۹× |
| سیاست k=0 (itr 499) | **0.080600** | **۲.۶۹×** |
| `all_UE` | 0.319593 | ۱۰.۶۸× |

برد/باخت per-graph در برابر `all_MEC`: **۰ برد / ۴۰ باخت**.

### 1.2 انرژی که سیاست واقعاً مصرف می‌کند

از `metrics_by_iteration.json`، کانال `total_energy`:
```
mean(g) = mean(violation) = +0.0973    (در ۵۰۰ از ۵۰۰ iteration مثبت)
mean(g) = (M - B) / S ,  B = 0.5·E_mec ,  S = E_mec
=> M = (1 + 0.0973) × 0.5 × E_mec = 0.5486 × E_mec
```
**سیاست ۵۴.۹٪ انرژی سیستم foreground مصرف می‌کند — یعنی تقریباً همان `all_MEC`.**

پس سیاست **قید را رعایت نکرده** (۱۰٪ نقض)؛ فقط از MEC فاصله گرفته بدون آنکه بودجه را برآورده کند.

### 1.3 صورت‌بندی ریاضی — علت دقیق

`all_MEC` انرژی سیستم foreground برابر **۱.۰۰۰ × E_mec** دارد (خودِ anchor است).
بودجه **۰.۵۰۰ × E_mec** است. پس:

```
all_MEC  =>  g = (1.000 − 0.500) / 1.000 = +0.500   → همیشه نقض
```

**`all_MEC` طبق ساختار غیرقابل قبول است.** تنها راه برآورده کردن بودجه این است که مصرف
انرژی foreground حدود **۲ برابر** کم شود → یعنی سیاست باید MEC را ترک کند.

### 1.4 تعادل Lagrangian — عدد دقیق

جمع‌بندی پاداش و پنالتی در هر اپیزود (میانگین ۵۰۰ iteration):

```
reward = (T_allUE_ref − T_policy)/D_G  −  Σ λᵢ · max(0, gᵢ)
```
| جمله | مقدار میانگین | یادداشت |
|---|---|---|
| میانگین `Average latency` (نرمال‌شده) | **0.2206** | جملهٔ latency |
| میانگین `constraint/penalty` | **0.0788** | پنالتی درون‌اپیزودی |
| `penalty / latency` | **۳۵.۷٪** | یعنی پنالتی بیش از یک‌سوم سیگنال را می‌خورد |
| λ_total میانگین | 0.9251 (نهایی ۱.۳۰۵۵) | |
| **λ* در مرز** | **≈ ۱.۳۰** | برابر با |

جملهٔ λ در نقطهٔ تعادل:
```
λ* = penalty / mean(g) = 0.0788 / (0.0973 − 0.0522) ≈ 1.30   ✓ (همان λ نهایی)
```
یعنی مسئله به نقطه‌ای همگرا شد که:
```
objective = 1.30 × (normalised energy) − (normalised latency)
```

|---|---|---|---|
| latency | 0.080600 s | 0.029931 s | **+0.050669 s** |

## 2. علت ریشه‌ای — یک تناقض در طراحی خودِ من

**این باگ من است، نه باگ آموزش.**

وقتی scope mismatch انرژی را رفع کردم (بخش B گزارش `V2_ACCEPTANCE_MATRIX.md`)، anchor را از
`E_ue` به `E_mec` بردم. اما **fraction را روی `0.5` نگه داشتم** و در گزارش نوشتم:

> «`--energy-budget-fraction 0.5` keeps its numeric value but changes meaning: it is now
> 0.5 × (the pure all-MEC plan's system energy)»

این یعنی بودجه را دقیقاً روی **نصفِ** مرجعِ مسئله گذاشتم. نتیجه:

* `all_MEC` غیرقابل قبول شد (نقض +۰.۵۰)
* λ اجباراً بالا رفت (به ۱.۳۰۵۵)
* قید از «قید» به **کنترل‌کنندهٔ اصلی** تبدیل شد (۳۶٪ سیگنال)
* سیاست به سمت `local` رانده شد: `action_fraction/local` از ۰.۱۲۹ به ۰.۴۴۶

در همان گزارش نوشته بودم که «fraction یک تنظیم مهندسی است، نه ثابت علمی کالیبره‌شده» — ولی
**هیچ‌وقت کالیبره‌اش نکردم.** این دقیقاً همان چیزی است که spec هشدار داده بود:

> «Do not choose B to force mixed placements or manufacture a win over all-MEC.»

و همچنین:

> «Investigate loose, tight, and intermediate budgets and possible infeasibility.»

این بررسی **انجام نشد**. من `0.5` را از کانفیگ قبلی نگه داشتم و فرض کردم چون scope درست شد،
بودجه هم درست است. نبود.

## 3. آیا شکاف ۴.۹٪ اجازهٔ برد می‌داد؟

`all_MEC` = 0.029931 و اوراکل پنل = 0.028452 → شکاف فقط **۴.۹٪**.
پس `all_MEC` تقریباً بهینه است؛ هر سیاستی که وارد مصالحهٔ انرژی شود باید **تقریباً به همان
نزدیکی** بماند تا رقابتی باشد. سیاست فعلی ۱۶۹٪ بدتر از all-MEC است — این یک شکست **کیفی**
است، نه یک باخت حاشیه‌ای.

نکتهٔ مهم: **اوراکل پنل از `all_MEC` بهتر است** (0.0285 < 0.0299) و آن هم با placement
مختلط. پس یک راه‌حل مختلط **وجود دارد** که هم latency کمتر و احتمالاً هم انرژی کمتری دارد.
سیاست آن را پیدا نکرد چون جست‌وجو در فضای `3^20` با سیگنال ضعیف ناکام ماند.

## 4. چرا جست‌وجو شکست خورد (علل ثانویه)

### 4.1 سیگنال پاداش ضعیف و انتها-محور
`_telescoping` در `spec/automotive_training/v2/env.py`:
```python
previous = self._schedule_slot(slot, [0]*n, validate=False).makespan_s
for k in range(n):
    prefix = actions[:k+1] + [0]*(n-k-1)
    current = self._schedule_slot(slot, prefix, validate=False).makespan_s
    rewards.append(-(current - previous) / l_scale)
    previous = current
```
جمع سری = `−(L_final − L_0)/D_G`. پس **کل پاداش فقط به makespan نهایی وابسته است**؛
تصمیم‌های میانی که makespan نهایی را عوض نکنند **صفر سیگنال** می‌گیرند.
مقیاس: `|reward| ≈ 0.22` در مقابل پنالتی `0.079` → نسبت سیگنال/نویز پایین.

### 4.2 فضای action عظیم و بدون ساختار
۲۰ گره × ۳ action = `3^20 ≈ 3.5e9`. action های میانی (mixed) با احتمال کمپین می‌شوند.
`all_MEC` یک راس مشخص از `3^20` است و هیچ چیزی در observation یا decoder آن را ممتاز نمی‌کند.

### 4.3 observation تمایزدهنده نیست
اگر بردار context برای گره‌های مختلف تقریباً یکسان باشد، سیاست مجبور است یک توزیع
تقریباً ثابت بدهد — که دقیقاً رفتار مشاهده‌شده است (`local 0.446`، `mec 0.352`، `v2v 0.201`).
**UNVERIFIED** — نیاز به اندازه‌گیری واریانس بردار context per-node دارد.

### 4.3 مشاهده: کانال‌های v2 **per-node نیستند** — تأیید شد

بررسی کد مسیر observation:

`spec/automotive_training/v2/env.py:473` — `_packed_observation`:
```python
rows = np.asarray(self.base._slice_current(self.base.encoder_batchs), dtype=np.float32)
...
ctxs = [self._context_vector(flat) for flat in range(n_rows)]
```
هر **ردیف** observation یک **گره/تسک** از گراف است، ولی بردار context **per-slot** است و
برای همهٔ گره‌های همان گراف **تکرار** می‌شود. نقل قول خود کد (`env.py:481-484`):

> «The frozen meta-sampler runs the env through MetaIterativeEnvExecutor, which sets ONE meta
> task (one graph) per call, so every returned row belongs to the SAME graph. **The per-slot
> vector is therefore the graph's context repeated over its slots**»

و `_contexts()` (`env.py:529`) هم صریحاً می‌گوید:
> «One v2 context per FLAT SLOT POSITION (never per dataset graph index)»

**نتیجه:** ۳۰ کانال context که اضافه شد (estimate age، per-node ε، queue/occupancy،
budget ratio λ، helper busy، link rates) **قدرت تمایز بین گره‌ها را ندارند** — چون یک بار
per-graph محاسبه و روی همهٔ گره‌ها کپی می‌شوند. تنها چیزی که بین گره‌ها فرق می‌کند
فیچرهای per-node نسخهٔ v1 است (workload، یال‌ها، criticality).

پس اگر قرار است سیاست تصمیم «کدام گره روی MEC برود» بگیرد، تمایز اصلی را **از فیچرهای
v1** می‌گیرد، نه از کانال‌های جدید v2. این علت ۴ را از «UNVERIFIED» به **تأییدشده** ارتقا
می‌دهد.

نکتهٔ ظرفیت: بردار packed در واقع **۱۰۹** بُعد دارد (۷۹/۹۱ نسخهٔ v1 + ۳۰ context)، در حالی
که docstring در `env.py:474` می‌گوید «91-wide» — docstring قدیمی است و باید اصلاح شود.

### 4.4 عدم تطابق آموزش/ارزیابی
 محیط ارزیابی از `v2_env_factory` ساخته می‌شود
(`spec/automotive_training/v2/stack.py:184-195`) که **`constraints_enabled` را پاس نمی‌دهد**.
پس در ارزیابی `constraint_manager = None` و **پنالتی انرژی صفر** است.

یعنی سیاست روی `penalized objective` آموزش دیده ولی من روی `pure latency` سنجیدم.
**این جدول را باید با این قید خواند.** (ولی conclusion عوض نمی‌شود: سیاست ۵۴.۹٪ انرژی
مصرف می‌کند، پس حتی در تراز انرژی هم برنده نیست — فقط ۴۵٪ صرفه‌جویی می‌کند و ۱۶۹٪ latency
می‌دهد.)

## 6. چه چیزی اول باید عوض شود

**۱ (بالاترین ارزش): کالیبره کردن بودجهٔ انرژی.**
فایل: `env/mec_offloaing_envs/scheduler/constraints.py`، تابع `budgets_and_scales`، شاخهٔ
`C_TOTAL_ENERGY` — و کانفیگ `--energy-budget-fraction`.

یک مطالعهٔ feasibility روی fixture های train/validation لازم است (همان که spec خواسته بود و
انجام نشد). نقطهٔ شروع منطقی: بودجه‌ای که `all_MEC` **قابل قبول** باشد، یعنی
`fraction ≥ 1.0`، و آن‌وقت قید فقط جلوی **بدتر از all-MEC** را می‌گیرد بدون آنکه سیاست را از
بهینه دور کند. مقدار دقیق باید از منحنی Pareto (latency در برابر انرژی روی پنل
کاندیدها) خوانده شود، نه حدس.

**۲: قابل قبول کردن پنل به‌عنوان یک مرجع.**
`all_MEC` و اوراکل پنل هر دو **غیرقابل قبول** زیر بودجهٔ فعلی هستند، پس سیاست تشویق می‌شود
بدتر از هر دو عمل کند. این نشانهٔ قطعی یک بودجهٔ نادرست است.

**۳: اگر قید واقعاً لازم است، آن را روی metric درست بگذار.**
اوراکل پنل (0.0285) از `all_MEC` (0.0299) **هم سریع‌تر است**. یعنی یک placement مختلط
وجود دارد که هم latency و هم احتمالاً انرژی کمتری دارد. قید باید سیاست را به **آن** سمت
هل دهد، نه به سمت «هر چیزی جز MEC».

**۴: قبل از هر iteration بیشتر، این را درست کن.**
۵۰۰ iteration دیگر هم این شکاف را نمی‌بندد، چون مسئله **کالیبراسیون** است نه **بودجهٔ
محاسباتی**. شاهد: `all_MEC` از iteration ۰ تا ۴۹۹ همیشه ۰.۰۲۹۹ بوده و سیاست هرگز به آن
نزدیک نشد (رگرت 0.0626 → 0.0521، فقط ۱۷٪ بهبود در ۱۵۰ iteration اضافه).

## C4. علت واقعی (رتبهٔ ۱)

**هدف meta، میانگین کیفیت انطباق روی ۱۰ توزیع با یک initialization مشترک است، و
تخصص per-task در هر outer step نابود می‌شود.**

شواهد کد (خودم تأیید کردم):

۱. `meta_trainer.py:~480` `UpdatePPOTarget` ده `meta_policy` را روی rollout **support**
   تطبیق می‌دهد، **سپس** `~528` rollout **query** جمع می‌شود، سپس `UpdateMetaPolicy`.
   پس سیگنال گرادیان meta از سیاستی گرفته می‌شود که **قبلاً تطبیق یافته**.

۲. `policies/meta_seq2seq_policy.py:1096-1099`:
```python
def async_parameters(self):
    for i in range(self.meta_batch_size):
        self.assign_old_eq_new_tasks[i]()
```
   این **core را به هر ۱۰ task policy اختصاص می‌دهد** و پارامترهای تطبیق‌یافتهٔ هر task را
   **دور می‌ریزد**.

۳. `spec/learning_ops.py:16-30`:
```python
scale = float(alpha) * float(k_steps)      # = 5e-4 * 3 = 1.5e-3
...
grads.append(acc / float(n))               # میانگین روی n task
```
   پس core با **میانگین جابه‌جایی ۱۰ task** حرکت می‌کند.

۴. **هیچ task embedding وجود ندارد** (grep روی `task_embedding|task_id_embed` → خالی).
   تنها هویت یک task، وزن‌های تطبیق‌یافتهٔ آن است — که در هر outer step دور ریخته می‌شود.

۵. حداقل meta-batch در `MRLCO.py:41-42` روی **۱۰** قفل است، پس این میانگین‌گیری **ساختاری** است.

**نتیجه:** تنها مکانیزمی که در زمان تست می‌تواند per-graph تخصص بدهد، **inner PPO سه‌مرحله‌ای**
است. و mix اکشن یادگرفته‌شده (`local .446 / mec .352 / v2v .201`) دقیقاً یک **سازش
hedged** است، در حالی که اوراکل **۶۷٪ MEC** است.

## C5. علت رتبهٔ ۲ — ۳ مرحلهٔ inner کافی نیست

شاهد درون‌اجرایی: `k3_regret` (0.0610) **بدتر** از `k0_regret` (0.0563) در انتهای اجرا.
و ارزیابی من: `k3−k0 = −0.004524` در itr350 (۳/۵ برد) ولی `+0.002151` در itr499 (۱/۵ برد) —
**علامت اثر با checkpoint عوض می‌شود.** مسیر k0 خودش از `_sync_from_core`
(`automotive_primary.py:651`) استفاده می‌کند، پس هر دو از core امتیاز می‌گیرند.

## C6. علت رتبهٔ ۳ — ظرفیت، نه قابلیت نمایش

فضای plan همهٔ `all-MEC` را **بی‌زحمت** بیان می‌کند (`3^20` شامل `1^20` است) و decoder
autoregressive با حافظه است. پس این **محدودیت نمایشی نیست — شکست یادگیری/conditioning است.**

## حکم

**انطباق در ~۶٪ اشباع می‌شود.** از k=2 به k=5 سیگنال **منفی** می‌شود
(k2 = 0.085048 بهترین، k5 = 0.090450 بدتر). اگر مشکل «بودجهٔ انطباق» بود (H5)،
k=5 باید بهتر از k=2 می‌شد.

**پس علت H2 است: core هرگز یاد نگرفته چه کار کند.** مکانیزم inner-step **قیدِ بایند نیست** —
قبلاً اشباع شده. بهترین حالت قابل‌دستیابی با هر k مجاز:
```
0.085048 s  =  3.22x کندتر از all_MEC (0.026452)
```

نکتهٔ ظرفیت: `k` در کد فقط `0/1/2/3/5` را می‌پذیرد (`automotive_primary.py:641-642`)،
پس k=10 یا k=20 **اصلاً قابل آزمایش نیست** — یعنی «آداپت عمیق‌تر» یک گزینهٔ عملی در این
پیاده‌سازی نیست.

**این H5 را نهایی می‌کند و H2 را تأیید:** با ۶.۶٪ حداکثر سود از انطباق، سیاست باید از خودِ
core خوب باشد. core خوب نیست چون میانگین ۱۰ توزیع بدون task embedding و با دور ریختن
پارامترهای per-task یاد می‌گیرد.
